Phone layout in a sentence: one sprint at a time, current sprint selected by default, the board's rows become a vertical list, and the two side panels collapse into accordions underneath.

Nothing on the phone is a different feature — it's the same three things (board, latest handoff, history) stacked instead of side by side.

What each region is, and where its data comes from

  1. 1Status bar. Which repo and directory is being watched, when the newest handoff landed, and when the monitor last polled GitHub. "Read-only" is a promise, not a mode switch.
  2. 2Sprint board. Laid out like your AMS Sprints slide: one row per sprint, stories left-to-right, checkpoint (Demo / Accepted) at the end of the row.
  3. 3Current sprint is emphasized. It's the row with in-progress work; earlier rows are all done, later rows are all planned.
  4. 4Latest handoff. The most recent handoff file rendered as-is, using the five sections from your handoff protocol: Context, What's done, What's next, Notes/blockers, Files/references.
  5. 5Handoff history. The files in the directory, newest first, with commit times. Clicking one would swap it into panel 4.
  6. 6Phone. Same status bar, compressed.
  7. 7Sprint picker replaces the multi-row board. Defaults to the current sprint.
  8. 8Accordions for handoff and history so the board stays above the fold.

Assumptions I made that you haven't told me yet

  • Story status (done / in progress / planned) can be derived from the handoff files — presumably "What's done" vs. "What's next" — rather than from a separate board file.
  • Sprint membership and story names are also recoverable from the handoffs, or from something else in the repo.
  • The checkpoint at the end of each row (Demo / Accepted) is recorded somewhere the monitor can read.
  • Handoff files are named or ordered in a way that gives sprint number and sequence.
